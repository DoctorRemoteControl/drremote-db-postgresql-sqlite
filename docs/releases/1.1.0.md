# DrRemote DB 1.1.0

PostgreSQL, SQLite, and DuckDB services for Java 17+ OSGi/Karaf applications.

- Optional JSON result/parameter support through a separate bundle and feature.
- QueryRunner single-row reads stop after detecting a second row; binding
  failures close statements and preserve original/suppressed exceptions.
- Optional native Hikari JMX management via `registerMbeans=false` by default.
  Pool counters, activation, reconfiguration rules, and cleanup are documented.
- Complex PostgreSQL migrations remain supported through the installed `psql`
  client. Real tests cover functions/DO blocks, psql meta-commands, COPY input,
  replay, failed-script rollback/history, and concurrent index transaction opt-out.
- SQLite batch/baseline/drift/readiness support and PostgreSQL migration
  coordination; DuckDB retains its explicitly documented simpler migration API.
- Binary Maven repository ZIP, SHA-256 checksum, source/Javadoc artifacts,
  examples, and installation guide; no retired private Maven server is needed.

## Requirements and installation

Use Java 17 or later, Karaf 4.4.11 (or a compatible OSGi runtime), and an existing
PostgreSQL database/user when selecting PostgreSQL. `psql` is required for
PostgreSQL script migrations. Third-party dependencies resolve from Maven
Central; DrRemote artifacts are provided in the release ZIP or built from source.

See [binary installation](../binary-installation.md),
[source installation](../installation.md), and [pool diagnostics](../diagnostics.md).

## Compatibility

Exported JDBC API packages and existing PostgreSQL/SQLite Maven coordinates are
preserved. The JSON adapter is optional and adds no Jackson dependency to the
existing database cores. Nested PostgreSQL/SQLite calls join the outer
transaction; an inner failure marks it rollback-only. DuckDB does not support
nested transaction callbacks or automatic DatabaseReady publication.

Migration histories remain application-owned. Do not edit applied migrations;
add a new version. psql and JDBC do not share one transaction, and opting a
script out of single-transaction mode requires its own partial-failure recovery.

Publishing this release is a separate maintainer action after validation; the
packaging script itself performs no deployment or runtime changes.
